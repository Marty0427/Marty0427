# PocketPass

An iOS app for keeping loyalty cards, boarding passes, tickets and membership barcodes on
your phone — scan a card once, and the code is there next time you need it, offline, with the
screen brightened so the till scanner actually reads it.

It is the Google Wallet idea, minus the account: everything lives on the device, there is no
server, no sign-in and no analytics.

![App icon](PocketPass/Assets.xcassets/AppIcon.appiconset/AppIcon.png)

## What it does

- **Scan a card** with the camera — QR, Aztec, PDF417, Code 128, Code 39, EAN-13, EAN-8,
  UPC-A, UPC-E and ITF-14.
- **Import from a photo**, so an emailed boarding pass or a screenshot works without printing.
- **Type a code in by hand**, with live validation and a preview of the symbol.
- **Show a card**: full-width symbol, screen brightened, auto-lock held off while it is on screen.
- **Organise**: categories, favourites, search across name, issuer, notes and the code itself,
  and expiry badges for tickets and coupons.
- **Lock the wallet** behind Face ID, Touch ID or the device passcode (optional).
- **Back up and restore** through a readable JSON file you control.

## Requirements

- Xcode 16 or newer (the project uses file-system synchronized groups, `objectVersion = 77`)
- iOS 17.0 or newer
- No third-party dependencies

## Build and run

```sh
open PocketPass.xcodeproj      # then ⌘R
Scripts/test.sh                # or: xcodebuild test -scheme PocketPass -destination '...'
```

Scanning needs a real device; the simulator has no camera, and the scanner says so rather
than hanging. Importing from Photos and every other screen work in the simulator.

CI builds the app and runs the 87 unit tests on a simulator for every push touching
`PocketPass/` — see [the workflow](../.github/workflows/pocketpass.yml). It needs no Apple
account and no secrets.

> **Note:** this project was written on Linux, with no Swift toolchain available, so it was
> first compiled by CI rather than by hand. The build and the tests pass; what no simulator
> can confirm is the camera scanner, the brightness boost and Face ID, which need a device.

## How it is put together

```
PocketPass/
├── App/          PocketPassApp, RootView, lock screen
├── Models/       WalletCard, BarcodeSymbology, CardCategory, CardTheme
├── Barcode/      validation, encoding and rendering (the part with all the standards in it)
├── Scanner/      AVFoundation camera capture, Vision photo detection, result mapping
├── Store/        CardStore, file and in-memory repositories, settings, backup
├── Features/     Wallet, Detail, Editor, Import, Settings screens
├── Support/      brightness, haptics, app lock, preview data
└── UI/           BarcodeView
```

Two rules shaped the structure:

1. **Anything with a standard in it is pure and testable.** Check digits, encoding tables and
   scan-result mapping have no UIKit, no camera and no disk, so `PocketPassTests` can pin them
   down. The EAN tables are additionally checked against the *rules* of the standard (right
   patterns are the complement of left-odd ones, G patterns have even parity, and so on), which
   catches a mistyped pattern that a hand-written expectation would happily enshrine.
2. **The renderer refuses rather than guesses.** A payload that cannot be drawn faithfully is
   an error with a message, never a symbol that quietly fails at the till.

Core Image generates QR, Aztec, PDF417 and Code 128. Everything else — EAN-13, EAN-8, UPC-A,
UPC-E and ITF-14 — is encoded here (`LinearBarcodeEncoder`) and drawn as whole-pixel bars
(`BitmapBarcodeRenderer`), because Core Image has no generator for them.

`docs/ARCHITECTURE.md` goes into the details, including why UPC-E is drawn as its UPC-A
expansion and how UPC-A is recovered from what the scanner reports.

## Shipping it

**[`AppStore/RELEASE.md`](AppStore/RELEASE.md) is the runbook** — accounts, keys, screenshots,
upload, and the fields only a person can fill in App Store Connect.

Release automation lives in `fastlane/`, authenticating with an App Store Connect API key
throughout (no Apple ID, no two-factor prompt, no certificate repository — signing goes through
Xcode cloud signing with the same key):

```sh
bundle install
bundle exec fastlane test       # unit tests on a simulator
bundle exec fastlane beta       # build, sign, upload to TestFlight
bundle exec fastlane release    # upload the build and the listing text from fastlane/metadata
```

`release` stops at "ready to submit" rather than submitting for review; pass `submit:true` when
you mean it. The same lanes run from GitHub Actions (**Actions → PocketPass → Run workflow**),
manual dispatch only.

Three things still need you, and cannot be automated: an Apple Developer Program membership
and API key, a first compile on a Mac, and screenshots from a real build.

The app icon is generated by `Scripts/generate_app_icon.py`, so it can be re-tinted without a
design tool.
